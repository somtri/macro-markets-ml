0.2 Cleaning: daily log returns

We compute daily log returns from the adjusted close price:

Return = log(adjusted_today / adjusted_yesterday)

This creates a stationary-ish series that’s easier to summarize and aggregate than raw prices.

sp500_daily <- sp500_raw %>%
  arrange(date) %>%
  mutate(daily_log_return = log(adjusted / lag(adjusted))) %>%
  drop_na(daily_log_return)

# sanity checks
dplyr::summarise(sp500_daily,
  start_date = min(date),
  end_date   = max(date),
  n_rows     = n(),
  mean_return = mean(daily_log_return),
  sd_return   = sd(daily_log_return)
)

2.3 Monthly market features + join with unemployment

Unemployment is monthly, so we aggregate daily S&P 500 returns to monthly features: - mean monthly log return (average of daily log returns within the month) - monthly volatility proxy (sd of daily log returns within the month)

Then we join on the month.

sp500_monthly <- sp500_daily %>%
  mutate(month_date = floor_date(date, unit = "month")) %>%
  group_by(month_date) %>%
  summarise(
    mean_log_return = mean(daily_log_return),
    sd_log_return   = sd(daily_log_return),
    n_trading_days  = n(),
    .groups = "drop"
  )

macro_market_monthly <- sp500_monthly %>%
  inner_join(unemp_monthly, by = c("month_date" = "date"))

6.1 ML setup: predict next month direction

We define a binary target: - next_month_up = 1 if next month’s mean log return is positive, else 0.

Features use only information available in the current month: - unemployment_rate - change in unemployment (this month - last month) - current month return and volatility

We split by time (train on earlier years, test on later years) to avoid leakage.

ml_data <- macro_market_monthly %>%
  arrange(month_date) %>%
  mutate(
    next_mean_log_return = lead(mean_log_return),
    next_month_up = if_else(next_mean_log_return > 0, 1, 0),
    unemp_change = unemployment_rate - lag(unemployment_rate)
  ) %>%
  drop_na(next_mean_log_return, unemp_change)

7 time split cutoff (feel free to change later)

train_data <- ml_data %>% filter(year(month_date) <= 2015)
test_data  <- ml_data %>% filter(year(month_date) > 2015)

8.1 Model 1: Logistic regression

We use logistic regression to estimate the probability that next month is “up”. This is a strong baseline because it’s simple, interpretable, and easy to reproduce.

logit_fit <- glm(
  next_month_up ~ unemployment_rate + unemp_change + mean_log_return + sd_log_return,
  data = train_data,
  family = binomial()
)

8.2 Evaluation: test performance + baseline

We evaluate on the held-out test period (years > 2015). We also compare against a simple baseline: always predict “up”.

# predicted probabilities for "up"
test_probs <- predict(logit_fit, newdata = test_data, type = "response")

# classify using 0.5 threshold
test_pred <- if_else(test_probs >= 0.5, 1, 0)

# confusion matrix
table(
  Actual = test_data$next_month_up,
  Predicted = test_pred
)
##       Predicted
## Actual  0  1
##      0  7 29
##      1 11 69
# accuracy
acc_model <- mean(test_pred == test_data$next_month_up)

# baseline: always predict up
baseline_pred <- rep(1, nrow(test_data))
acc_baseline <- mean(baseline_pred == test_data$next_month_up)

c(model_accuracy = acc_model, baseline_accuracy = acc_baseline)
##    model_accuracy baseline_accuracy 
##         0.6551724         0.6896552

In the held-out test period, the logistic regression model achieved about 65.5% accuracy, while a naive baseline that always predicts an “up” month achieved about 69.0% accuracy. This indicates that the simple feature set used here (unemployment level, unemployment change, current-month return, and current-month volatility) does not provide strong predictive power for next-month market direction. This result is expected in real financial data because returns are noisy and many drivers are not captured in a small macro-only feature set. The model is still useful as a transparent baseline and as a demonstration of a time-respecting ML workflow.
